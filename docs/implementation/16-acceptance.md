## Emergency recovery: what was actually verified

The controlling [#9 distribution contract](https://github.com/Benson-mk/tsdm-ui/issues/9#issuecomment-6239001718) says to qualify emergency native recovery “independently of successful app startup and ordinary preference storage,” including exact-post anchors and re-entry. It explicitly allows first-version disable/uninstall/native recovery.

The installed run temporarily disabled the script, used the native bypass destination with its exact fragment, confirmed native access, then re-enabled the script and deliberately re-entered the application. The installed enabled-script manager command also preserved a subsequently selected fragment. The bypass is excluded by userscript metadata and respected by runtime startup, so it does not require a successfully mounted layout, functioning application command or stored preference. These observations verify the required startup-independent recovery outcome.

This was **not** an injected synchronous bootstrap exception. The automatic catch-path recovery link was not independently forced and is not marked tested. Adding an internal DOM/host mock solely to enter that branch would not strengthen the verified emergency path within the confirmed network-edge E2E boundary, so no such test was added. Later release qualification must repeat recovery on every required installed environment and preserve then-applicable writing/unknown-attempt state.
