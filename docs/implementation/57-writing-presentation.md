## Actual trade-offs

1. Keep one editor DOM view mounted per writing context while reading hides it with `v-show`; context replacement still creates a new view. This retains native view state and avoids presentation remounts at the cost of retaining hidden editable DOM and its subscription for the lifetime of that context. Automatic focus remains visibility/preparation/composition guarded.
2. Let the maintained layout own compact/expanded presentation as transient state, defaulting replies to compact and new threads/edits to expanded. This avoids adding content revisions or another recovery field; after a reload, presentation returns to the action default while writing recovery keeps its existing contract.
3. A compact writing pane and reader share the remaining viewport, with the pane bounded to48dvh and independently scrollable. Expanded writing uses the available area and hides the reader. This preserves nearby reading for short replies while requiring scrolling within compact writing for the existing tools/options; their simplification remains ticket58.
4. Reserve the explicit size and Return to reading strip outside the scrolling writing body, and restore the active editor selection/focus after a deliberate size transition. Reserving its height reduces the body viewport while keeping the controls reachable and preventing focused source/visual/other fields from scrolling underneath them. Browser resize alone neither changes presentation nor takes focus.
5. Use an accessible native disclosure for the retained-context destination summary and show relevant account/recovery/attachment/pending/conflict/ambiguous-conversion/financial warning summaries outside it while reading. Detailed operations remain in the same writing view, reached with Return to writing. This adds a disclosure step for identity while preserving the ordinary reader budget; active warnings still use reading space and long warning sets can scroll; no second context/store or operation path is added.

6. Reuse the existing editor message translator for the retained ambiguous-conversion summary. This keeps wording and all supported translations aligned while adding a maintained-layout dependency on editor message translation.

7. Historical de64 candidate prevented default mousedown focus transfer on the two presentation controls while composition was active. This preserved Blink composition but failed the physical macOS candidate check; it was removed under the owner decision below. Its original cost was suppressing pointer focus on those buttons during composition. This is retained as an abandoned implementation trade-off, not current behavior.

8. Accept native candidate cancellation on a deliberate presentation switch, retaining the unfinished raw input and already committed text rather than preserving the active candidate. This follows the owner’s product decision and restores ordinary pointer focus behavior. The user must begin composition again to convert the retained raw syllables. Existing guards still defer keyboard/programmatic presentation requests while composition remains active; focus, continued editing and undo/redo remain required.
