## Operation-specific API decisions

- Directory/group: prefer page JSON for structured identity and a consistent response envelope. Accepted #8 directory parity supports this choice; its sample was approximately 1% larger compressed, so no transfer-saving claim is made.
- Board/subordinate board: prefer page JSON for structured metadata and accepted populated-row parity (sample compressed size about 6% lower). Parse the returned HTML meaning; do not force `forumdefstyle=yes`, which changes a native cookie preference.
- Thread/page: preserve #16's page JSON path with accepted PID/content parity and approximately 47–53% lower sampled compressed size.
- Exact post/last reply: evaluate JSON-preferring canonical resolution where final destination is observable; retain the accepted same-tab document-navigation strategy for unobservable redirects. Never infer a page from floor count or choose the last currently loaded post as a substitute for a canonical last reply.
- All operations consume useful HTML returned by the same JSON-preferring read. No second representation request follows a challenge, permission, malformed or missing result.

## Trade-offs

1. Reuse the pinned experiment's extraction rules through portable parse5 models while replacing its navigation policy: preserves learned forum details but requires authored fixtures and installed qualification for the new boundaries.
2. Keep returned filters/pages as explicit links instead of synthesizing combinations or page counts: faithfully preserves supported criteria, but unusual unrecognized URLs remain native links or explicit unavailable outcomes.
3. Use native disclosure/selection controls for the board picker and existing Reka About dialog: sufficient platform keyboard behavior with fewer overlay primitives; visual presentation must remain consistent and the actual installed native control still needs observation.

## Storage and future-work boundaries

The current navigation host owns one serial save queue for one namespaced, versioned browser sessionStorage record. Future writing recovery must extend this same owner rather than add another writer or storage channel. No cookie, form token, unuploaded file bytes, search request or notice request is stored or implemented here. Snapshots are temporary observed results, not a durable reading-history collection. New document navigation is attempted at most once per entry before explicit native recovery. Actual session-storage acknowledgment, remount, Back/Forward and startup-independent manager recovery remain installed gates.
