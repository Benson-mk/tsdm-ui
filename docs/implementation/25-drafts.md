# Forum drafts — issue 25

## Before implementation

The confirmed application seam is real layout → workspace → public forum client → browser host; tests replace only external HTTP. Fresh list, thread marker and edit-source reads independently establish same-record storage. Raw response callbacks are candidates, never confirmation. Existing thread attempts provide account/revision/duplicate guards. Thread drafts are distinct from local writing recovery.

Failure inventory: absent/ambiguous list template; a returned row lost by local filtering; duplicate thread identities; pagination under another filter or account; malformed/unsupported response; login/challenge/permission/throttle/network failure; attacker-authored draft text or edit link; stale list selection; vanished/public/moderated draft; different actor/board/opening post; incomplete source/options/reference metadata; stale save token or changed controls; duplicate activation; write response loss; failed independent readback; same-record source mismatch; remote concurrent edit; session generation change before/during send; newer local edits while saving/publishing; refreshed pending attempt; save-and-continue racing newer writing; local discard deleting remote work; publication leaving a draft or moderation; missing public-result identity; attachment upload lifecycle accidentally expanded.

Named expectations are added immediately before each corresponding implementation slice. No live forum writes or installed qualification is claimed by synthetic cases.

## Implemented behavior

The public forum client reads a complete returned draft page and its offered pager, resumes through fresh draft-list membership, native unpublished-state evidence, owned opening-post identity and a complete edit-source read. Native input remains inert. Save uses a read-only `prepareDraftSave` step to capture the current account's complete returned-list baseline, then consumes the exact prepared immutable attempt once. The workspace acknowledges that token-free attempt before sending. Save uses the native `save=1` control; publication uses the current same-record edit submitter and empty `save`, never the possibly effectful `pubsave` link.

A callback supplies only a candidate. Confirmation rereads the list, exact thread/post/author/board and whole stored source/options/reference metadata. New-save checks refuse identities in the pre-send baseline; resumed saves retain the same identity and compare the earlier full stored revision before writing. Publication requires matching current saved content and a fresh same-record form, then distinguishes an independently confirmed public post, remaining draft, reported moderation and uncertainty. Known blank-price normalization follows issue 20's shared verification contract. Initial activity instructions are not persistent stored fields and are not repeated when absent from the current edit form.

The workspace exposes explicit list loading, full returned rows, pagination, resume, save, publication and selected-record checking of uncertain attempts. One retained composition guards replacement; Save-and-continue advances only after independent confirmation of the relevant unchanged revision. Pending refresh retains the original attempt and baseline as uncertain, without replay. Local edits made after send remain in the editor. Local discard never issues remote deletion. No upload, file association mutation or removal UI is added.

## Actual trade-offs

1. Draft operations reuse the current native-control serializer and stored-source verification from ordinary publication. This avoids conflicting control rules, but adds a narrow save/publish mode to the serializer and requires ordinary-publication regression coverage.
2. Opening Drafts presents an overview with explicit Load. This makes account-specific network access deliberate and adds one activation before viewing the list. Confirmed publication separately refreshes the list as part of reconciliation.
3. Preparation, membership and absence checks traverse every returned draft pager rather than assuming the first page is complete. This adds GET latency and traffic. An unsupported page is a failure, never proof of absence.
4. A distinct read-only preparation boundary retains the pre-send list baseline before any write. It adds one public API step and in-memory one-use state, but preserves usable original-attempt evidence across a pending-response refresh.
5. A stored version is the complete observed source/options/reference snapshot, not a server-side atomic revision token. Preflight detects observed remote changes; ambient sessions and other tabs can still change between reads and effects. A new matching draft absent from the baseline does not rule out a simultaneous same-content write elsewhere.
6. The existing URL-encoded host transport sends the native edit form's successful controls for Save and Publish. This reuses the already qualified text transport and excludes file bytes; historical multipart draft evidence is a semantic lead, not proof of this candidate's native wire compatibility. Current ordinary draft qualification remains mandatory.
7. Unknown/ambiguous current forms, source mismatches and incomplete authoritative state remain unconfirmed. This can require native inspection rather than guessing a successful save, publication or empty list.
8. Initial feed/activity instructions remain in retained attempt history but disappear from the saved-draft options UI; updates use only controls offered by the current native edit form. No feed or notification delivery is claimed. Their nonpersistent semantics remain distinct from the stored thread revision.
9. Existing recognized attachment reference fields are preserved unchanged and independently compared. Upload/association/removal remains in its explicit extension ticket; unrecognized controls are refused rather than inventing ownership or silently deleting references.
10. Confirmed publication retains the writing context and attempt history while opening the actual result, including any later local revision. This keeps original evidence/source available and consumes page-session space instead of eagerly clearing the context. A completed publication guards only its original context/target; retained completed history does not block a deliberately prepared unrelated composition. Unresolved earlier attempts still require original-result checking.
11. Draft lists currently remain account-bound in-memory workspace state, while writing and attempt evidence use the existing acknowledged page-session record. Reload requires explicit list loading again; it does not silently replay list or write operations.
12. The portable client advances to 0.7.0 because adding required draft methods changes the structural ForumClient contract. The app remains 0.4.0; separate consumers must pin and migrate the client artifact, while userscript installation follows its independently verified bytes.

13. Native HTML/forms supply consequential draft preparation and readback because current source evidence establishes their meaning, while no structured draft-write benefit was demonstrated. The public reader still accepts useful JSON-wrapped HTML. This avoids speculative endpoint semantics but keeps template compatibility and transfer costs.
14. Publication checks reconstruct a canonical same-origin thread URL from validated numeric identities, ignoring retained URL decorations. This confines host requests and confirmed links to the configured forum, at the cost of not preserving optional view parameters from an external caller's retained URL.
15. After an original-attempt check remains inconclusive, a separately warned manual resend uses the current revision and a new immutable attempt linked to the old one. This restores the accepted recovery path but can duplicate content or native creation effects; no empty list, refresh or later success resolves the original unknown attempt. The warning is invalidated by revision, target or account changes.

## Completed-review repairs

Current Save capability is checked again at dispatch using the existing successful-control decoder. Publish keeps its separate native-control requirements. Selected mention identities reuse the shared preflight resolver; actual resumed draft identities select their edit form, then account, stored version and current controls are observed again after the awaited lookup. Exact stored-source verification still refuses unqualified mention rewriting. This inherits the existing mention preflight's extra GET/lookup latency; it adds no distinct trade-off beyond the shared current-form verification and uncertainty rules already recorded above. Standards found no material issue; both Spec findings were validated by the BDFL and corrected with 14 failure-first application cases.
