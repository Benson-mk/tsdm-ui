## Decomposition trade-offs

1. Twelve bounded deliveries keep each change demonstrable in a fresh context, at the cost of more issue/dependency tracking than a few large tickets.
2. Reusing the existing controllers avoids a speculative broad prefactor, while leaving shared-layout coupling to small preparatory changes within affected slices.
3. Six unblocked slices preserve scheduling freedom; concurrent changes to shared layout code still need merge/integration coordination. Shared files alone are not functional blockers.
4. Page picking follows the new header, all-column resizing follows the wide writer, and board checking follows thread-check coordination. These gates serialize those parts but avoid competing temporary entry points or request/lifecycle contracts.
5. Group mapping is usable early; complete reading/writing palette and safe-edge composition follow the surfaces they require. Intermediate builds can have partial visual refinement until later slices land.
6. Each feature owns its verification, with a separate final mixed-journey ticket. This adds an integration step while retaining local accountability and cross-feature evidence.
7. The owner-selected Edge-first cadence reduces repeated cross-browser checks during feature delivery, while deferring discovery and possible remediation of Chrome-specific defects to final integration. Final qualification still requires both browsers on the same candidate.
