# Accessible attachment downloads — issue #28

The reader offers Download for an unambiguous native attachment identity and its offered filename link. Qualified current profiles are an `attach_ID` wrapper and a `dl.tattl > dd > p.attnm` filename with `a#aidID`, including a native file list outside `#postmessage`. Conflicting identities are refused; payment-record links are not filename capabilities. Activating that filename follows the same checked path. The forum client re-reads the containing Thread with a fresh request, confirms the expected current account and the same Post/attachment identity, then receives the newly offered opaque URL once. Binary requests do not add `tsdmapp`, follow redirects, or invoke purchase routes. Native price/access text remains text; an attachment link is not a claim of free access or ownership.

The workspace keeps one ephemeral download attempt. It rejects login, challenge, permission/payment refusal, missing file, markup/response documents, empty payloads, incomplete lengths and failed transfers before exposing Save file. Refresh, navigation and Back invalidate pending completion and prevent a cancelled access check from dispatching a later binary request. Repeated activation while receiving does not duplicate the request. An in-flight request already sent to the server cannot be rolled back.

Save file uses the browser's Blob download handling in the original user action. Its status is **Browser save requested**, with explicit instructions to check Downloads; it never claims the file reached disk. A browser refusal/cancellation remains unconfirmed. Prepared bytes and object URLs are not stored in recovery and do not survive reload. Restored attachment descriptors must pass the existing recovery validator and a fresh access check before receiving bytes.

The ordinary native `ignore_js_op` wrapper is transparent under the existing inert-content projection. Download feedback and Save remain next to the selected Post attachment, and completed preparation scrolls that feedback into view. Unsupported native actions remain available through the existing native continuation.

## Failure inventory and test-first slices

The named `J8.download-*` application E2Es cover: exact ordinary saved-file bytes/name/hash; current opaque-token replacement and already-accessible paid fixtures without purchases; current access loss and account change; HTTP login/challenge/permission/payment/HTML/JSON/missing outcomes; malformed MIME including UTF-16 and long markup preambles; incomplete/aborted transfer; unsupported or repeated URL arguments and duplicate identity; filename activation; restored and malformed recovery; stale in-flight and pre-dispatch navigation races; duplicate activation; actual browser download refusal; transparent native wrappers and a deep Post Save action. Only external HTTP is substituted. Tests save and reread actual browser files. The local TLS/cache journey preserves the fresh-access behavior; it is not evidence of a reproduced installed-cache defect.

Implementation began after a recorded missing-Download RED case. Subsequent classifier, unsafe-link, recovery, repeated-activation, cancellation and usability failures were retained before their corrections. No unit-test layer was introduced. The evidence reporter retains authored saved-file bytes and JSON file receipts alongside screenshots, source hashes, scenario copies and its manifest.

## Actual trade-offs

1. Browser Blob download handling avoids additional manager grants or a new file-picker capability. It provides no trustworthy page-level disk-completion callback, so the product reports a request and acceptance uses independent browser/filesystem evidence.
2. Receiving and validating the complete file before a separate Save action prevents response pages from being handed directly to browser download handling and retains a real save gesture. It uses memory proportional to the file and requires another click; no arbitrary attachment size limit is imposed. Memory/transfer failure stays explicit.
3. Fresh containing-thread revalidation costs one additional read per deliberate download. It avoids treating old account-sensitive attachment tokens or restored snapshots as current access, while retaining the inherited limit that ambient-account changes are not atomically isolated from a request already in progress.
4. Direct, same-origin, unambiguous native attachment links are the qualified capability. Unknown arguments, active click handlers, purchase links and redirects are refused instead of guessed. Markup-leading, HTML and JSON/XML response documents are conservatively withheld, including a legitimate file whose bytes cannot be distinguished from such a response; native verification remains available. Empty payloads are also withheld, so a legitimate empty file cannot be saved through this path. This costs coverage for ambiguous formats, empty files and unqualified link profiles.
5. Download state is intentionally ephemeral and only one attempt is presented at once. Reload or navigation requires a deliberate new download, which avoids restoring binary data or replaying an old attempt in the shared page-session record.

Inherited architecture, page-session ownership and development-versus-release qualification choices remain in ADR0001–0003; they are not new #28 trade-offs.
