## Ticket #53

Original record: [53-responsive-navigation.md](53-responsive-navigation.md).

53.1. Narrow navigation uses an **inline nonmodal disclosure**. Opening keeps focus on its button, Tab follows the ordinary page order, and Escape closes it and returns to its button through the existing composition guard. This keeps the editor and reader mounted and avoids a second portal/focus boundary; the disclosed controls temporarily consume reader height, and the page remains keyboard reachable rather than trapping focus.

53.2. **Settings stays directly reachable** beside the account and navigation entry. Its persistent row costs space but keeps appearance adjustment available without opening navigation. Final ordinary chrome is 185.1875px, within the 240px budget.

53.3. Direct wide-thread arrival **retains orientation rails while reclaiming only the absent results track**. This preserves familiar board/destination access while using less width than a completely rail-free reader; populated board/search/favorite/notice result contexts keep their existing panes.

53.4. The existing **959px breakpoint is reflected in the layout's resize state** as well as CSS, so control availability and expanded state can be exposed accessibly without a new navigation owner. These two expressions must remain aligned. Resizing changes shell presentation only; it does not enqueue an action in the writing owner's single deferred-intent slot or replace the editor.

53.5. Expanded reading width exposed **fractional scroll-rounding accumulation** across appearance changes. Retaining each anchor's intended offset and pane top, in addition to its node and actual scroll position, adds two transient measurements while preserving its original position across repeated reflow. A deliberate reader scroll still establishes a fresh anchor. Navigation disclosure and viewport changes rebase the retained appearance sequence so an old absolute coordinate is not reused in a new pane frame.

## Ticket #58

Original record: [58-authoring-tools.md](58-authoring-tools.md).

58.1. Keep seven frequent operations directly named in the ordinary surface: Bold, Italic, Underline, Strike, Unordered list, Ordered list and Code. The remaining supported operations take one deliberate advanced-disclosure step. This reduces ordinary configuration and persistent tool density while making less frequent operations less immediate.

58.2. Use one native disclosure with named fieldsets for text appearance, links/media, quotes/hidden content, tables and mentions. The same desktop groups wrap at smaller widths instead of becoming a mobile sheet. Native keyboard disclosure avoids another dialog/focus lifecycle; opening the full advanced set uses more vertical scrolling than opening a single narrow tool group. The retained editor DOM/history stays mounted, and disclosure state is transient rather than recovered.

58.3. Parameterized tool selection reveals one command-specific argument field and a named Apply action; changing the selected parameterized tool clears its unapplied argument. Commands without arguments dismiss the previous field. This prevents irrelevant/stale values leaking between tools, at the cost of re-entering an unapplied value when returning to a different tool.

58.4. Actual formatting retains the established source-selection-to-visual command path and focuses the visual editor after the command. Source-first initialization, explicit mode switches and inert disclosure remain. This avoids adding a second source transformation/eligibility path; a successful formatting command initiated in source mode still activates visual mode, as the previous generic Apply did. Active mode has an accessible pressed state plus visible weight/outline. A later exact differential confirms that this unchanged command path can also mark the following CRLF at a selected line boundary; both CRLF byte sequences remain intact. That inherited serialization boundary is retained here rather than silently normalizing supported source semantics.

58.5. Move the existing mention search/results presentation into the editor's named advanced group, keeping the same workspace methods, current native identity resolution and account/composition guards. This removes a permanently visible remote-tool area while adding mention presentation to the editor component; it neither adds a resolver nor changes attachment/operation ownership.

58.6. Keep ordinary post options visible under the ticket's optional “may be disclosed” scope. This retains their current visual density while avoiding hiding meaningful selected/disabled values and financial/access settings in a new disclosure. Account, recovery, conflict, conversion, pending/uncertain and financial warnings remain outside the closed advanced group.
