## Complete request → selection → model → visible workflow

1. `ThreadRepository._fetchAnswer` builds `forum.php?mod=viewthread&tid=…&page=…`, retaining `authorid`, explicit `ordertype` or an exact order override. With only a PID it asks `mod=redirect&goto=findpost&pid=…`. It keeps a plain URL for sharing/reload and sends the same route with `tsdmapp=json`. `withTsdmAppJson` places the parameter **before** a fragment and leaves AJAX XML routes alone. No new structured read endpoint or authentication scheme is introduced. [Request builder][requests] [URL/decoder helper][page-helper]
2. On a successful HTTP response, `fetchThreadPage` calls `threadApiAnswerOf`. A successful schema-3-or-later **thread** answer becomes `threadPageFromApi`; its whole-page `document` is not parsed. A forum message with `ok: 0`, `error: message` and either the numeric schema or integer `login` is also accepted. Web HTML, older page JSON, `error: unknown` and failed builds take the document/error path. [Repository selection][repository] [Selector][selector]
3. `threadPageFromApi` builds the existing `ThreadPageInfo`, mapping canonical thread/board identity, title, breadcrumbs, pagination, closure/draft/moderation, reply parameters and `Post.fromApi` results. `Post.fromApi` uses fields for identity, author, timestamps, capabilities/URLs and rate metadata; rich body and plugin HTML remain. [Page model][page-model] [Post model][post-model]
4. `ThreadBloc` uses the same page model for initial load, page changes and author filtering; it discards superseded/account-invalid loads. `ThreadPage` uses this state to show content, login/permission outcomes, returned page controls and post cards. This is an executable native-client path, not proof of the browser adapter's behavior. [Bloc][bloc] [Visible client][client-view]
5. In the delivered UI, `createForumClient.readPage` makes one JSON-preferring read, decodes the response, updates its account generation and returns serializable models. `decodeThread` **requires a string `document`**, combines it with `head`, checks response origin and requested/returned/canonical TID, extracts account evidence, builds posts/rich nodes/attachments, and finds returned filters/pages. Workspace owns origin/results/selection/position and layout owns rendering/focus. The layout renders `ContentView`, post PID anchors, missing-target alerts and attachment controls. [UI client][ui-client] [UI decoder][ui-thread] [UI layout][ui-layout]

A populated route can therefore change from “JSON → rebuild page → selectors → post model” to “JSON → validated fields plus retained inert fragments → post model.” Returning to results and saving a file still cross the workspace/host boundaries; a new metadata representation does not complete those journeys.

## Attachment continuity with delivered #28

The existing attachment chain is **containing thread → exact post → unambiguous attachment → native same-origin download URL → fresh access/account check → binary response → separate browser Save → independent file evidence**. `attachments(wrapper, response.url)` searches `attach_<id>` containers or `dl.tattl / p.attnm / a#aid<id>`, requires a single unambiguous anchor/name, rejects scripted/pinging links, and accepts only same-origin `/forum.php?mod=attachment&aid=…` with the limited existing optional query keys. It returns ID, name, URL and surrounding details. The post/thread/account context lives outside that small descriptor. [Attachment extraction][ui-attachments]

`downloadAttachment` rereads the containing thread with `{ fresh: true }`, confirms the same nonunknown account and exact post/attachment, then uses `requestFile` on the newly offered native URL. It rejects changed generation, redirects and response-like/error content. It does not add `tsdmapp` to binary URLs and does not purchase access. [Current access/readback][ui-download] [File validation][ui-file] [#28 implementation record][downloads-record]

Schema 3 supplies no attachment array in the inspected post builder/fixture shape. A future reader must preserve the native attachment HTML wrappers/anchors and resolve them against the actual forum response URL, then feed the existing serializable attachment/context contract. `thread.pay` is a thread-content charge and does not establish that an attachment is already accessible. A generic “attachment present” icon, a PID or a body text link alone cannot replace the current extractor's evidence. If the new fragments omit the required controls, keep the usable same-response document for that operation or report the unsupported capability; do not silently remove Download controls or manufacture targets.

The inspected `thread_v3_edited` body includes an image attachment and a hidden image-tooltip download link with `mod=attachment`, name/size text and a native encoded `aid`. Its wrappers are `aimg_<id>` / `aimg_<id>_menu`, rather than the `attach_<id>` or `dl.tattl / a#aid<id>` forms accepted by the delivered extractor. This is meaningful retained attachment HTML but does **not** establish equivalence for #28's supported ordinary/already-accessible-paid file controls. The other inspected variants expose no matching direct-file control markers. #28's earlier fixture/file/installed outcomes remain under its original candidate; they do not qualify a new reader. Required downstream cases include ordinary and already-accessible paid attachments in body fragments, response-side permission wrappers, duplicate/ambiguous IDs, native query preservation, account changes during the fresh read/file receive, and delivered bytes. This ticket repeated no file downloads.

## Exact targets, redirects and passive return

Schema metadata helps identify the returned TID/PID/page and `share_url`, but it does not reveal a redirect fragment hidden from a browser fetch. The native client follows its own network stack: notice targets now select schema 3 and locate the requested PID; older answers parse a document and use `resp.realUri` for the redirected page. The native notice detail retains a report target only when the returned thread matches the intended thread. This is useful identity evidence, not a substitute for the UI's stricter exact-destination behavior. [Notice target reader][notice-reader]

The delivered UI preserves the requested PID and thread hint, distinguishes floor/page/PID, checks returned identities and shows a missing-post alert instead of choosing another post. Last reply uses authoritative returned boundary/order/floor evidence only when sufficient; otherwise it requests canonical `goto=lastpost` resolution. An opaque redirect requests a same-tab full-document navigation. Workspace persists its pending entry before the host's `location.replace`, bounds resolution to one document navigation, and remounts from the accepted page-session record. History contains a safe overview plus opaque key; snapshots preserve original results, effective criteria/page, selection and useful position. Back/Forward/reload restoration uses the retained snapshot without automatically repeating Search or notice reads; missing/incompatible/account-mismatched snapshots require explicit reload. [UI target rules][ui-thread] [Workspace][ui-workspace] [Browser host][ui-host] [Accepted storage contract][storage]

Keep this split: forum client owns canonical identities/response interpretation; workspace owns result-return context and invalidation; host owns actual navigation/storage; layout owns focus/position presentation. A future structured adapter must be exercised through these same boundaries. #17's earlier installed observations establish only its declared candidate, browsers/manager and development scope. New executable bytes need affected acceptance checks in Chrome and Edge; stable-manager/Windows/full-release gates remain separate.
