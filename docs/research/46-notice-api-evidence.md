# Standard notices: tsdmapp 1.9.0 integration evidence

Date: 2026-10-20 (Asia/Hong_Kong). Implements the evidence deliverable in [#46][ticket], informing the open [notice workflow #31][notice-ticket] under [implementation specification #15][spec]. It does not implement #31 or qualify an application release.

The newer `notify` contract can supply the full HTML body and target links of each returned notice without loading the notice page. It does not establish a complete, paginated standard-notice inbox. The inspected native client deliberately fetches a recent window and automatically acknowledges notices, including notices it does not retain in that window. Preserve deliberate category/page HTML reads for the browser's complete inbox until a server-owned contract and populated observations establish equivalent API coverage. Treat a future `seen` call as an explicit account-wide read effect, separately from content loading and private-message prompts. ## Request → selection → model → visible workflow

### Content and capability

1. The native refresh event enters `NotificationBloc._onUpdateAllRequested`, requires its current user's UID, loads that account's previous bound and calls `fetchNotificationV2`. The repository uses the supplied native HTTP client/account, computes `since`, then asks `GET plugin.php?id=tsdmapp:api&action=notify&since=…`. First load and manual refresh also ask `notify`; refresh bypasses the polling skip gate. [Refresh entry][refresh-entry] [Fetch selection][fetch-selection]
2. `TsdmAppApi.ask` accepts a JSON object with integer `ok`. A login response remains an answer; missing/non-JSON or `error: off` installs a one-hour negative capability cache. `error: action` means that action is unavailable, not that the whole plugin is absent. Network failure/HTTP 429 yields no answer for this call. The ordinary `notify` path uses `ask`, not the waiting/retrying `askWaiting` policy. [API policy][api-policy]
3. `notifyGateOf` distinguishes `error: login`, something-new/unknown, and nothing-new with a server timestamp. It considers notice `dateline`, any unread broadcast, and PM timing signals. A successful old `notify` is a polling gate, not the newer direct-list capability. `notifyCarriesLists` requires `ok == 1`, string `formhash`, list `notices`, list `announces`, integer `time` and numeric `timeoffset`. It does **not** check `version`, `api`, positive `uid`, category, paging, row validity or list completeness. Thus this predicate cannot establish the browser's account binding or complete inbox coverage. [Gate][notify-gate] [Capability guard][api-lists]
4. On that capability, `_fetchWithApiLists` converts every map row through `Notice.toV2FromApi`, drops failed conversions, and then time-filters the list. On an older/missing answer it reads the notice, PM and broadcast pages in parallel, adding `tsdmapp=json`; notice-page loading retains its server read effects. Missing page content fails instead of becoming empty. `error: login` short-circuits before fallback. [Fetch selection][fetch-selection] [API-list path][api-list-path] [Page validation][page-validation]
5. `Notice.toV2FromApi` requires integer `id`, integer `dateline`, string `note`. It reconstructs a detached notice element to reuse body-link/image normalization and ignore-target parsing. `note` is the returned full HTML body, not the `text` preview. It creates `NoticeV2(id, timestamp, data, alreadyRead, ignoreType, authorId)`; `new == 0` becomes read, other values become unread. Missing `authorid`/`type` can leave ignore metadata unknown. Category, `from_id`, `from_idtype` and `from_num` are not retained in `NoticeV2`. [Row conversion][notice-conversion] [Model][notice-model]
6. The bloc persists and reconciles the fetched rows by account, then reads its accumulated local cache. Its read-state policy treats a first-seen item inside an established fetch window as locally unread even if another device already cleared the server flag; a newer revision of the same notice ID is new again. A stored local mark is therefore not an authoritative server unread count. `NotificationPage` renders the stored notice list with `NoticeCardV2`; the card renders the HTML body and its links. Its local read/unread controls do not establish a server mark-unread operation. [Reconciliation][reconcile] [Persist/cache][persist-cache] [Visible page][notice-page] [Card][notice-card]

**Auth/account implication (recommendation):** bind a browser read and any acknowledgement to the forum client's current account generation and verified positive UID, and invalidate actions after an unknown/conflicting/changed identity. A formhash alone is insufficient: the direct-list guard does not validate UID, and the native per-account cookie clients are different from the browser's shared current-account session. Never publish or persist live tokens in a navigation snapshot. Existing UI thread decoding already reconciles numeric envelope UID with inert header identity and treats conflicts as unknown; use its ownership model when #31 adds notices. [UI decoder][ui-decoder] [ADR ownership][adr]

### Bounds, categories and time

The upstream synthetic response builder includes `ok`, `api: 1`, `version: 1.9.0`, `uid`, `formhash`, Unix server `time`, forum member `timeoffset` in hours, `counts`, `pm_last`, `notices`, `pms` and `announces`. A notice row includes `id`, `new`, `type`, `category`, author fields, `note`, `text`, `dateline` and origin fields. This is evidence of the consumer's expected fields, not an exhaustive server schema. [Meaningful response builders][fixtures-shape]

The repository clamps an absent, old, or implausibly future lower bound to approximately three days ago; a stored bound up to ten minutes ahead of device time can still be accepted. It then retains notice rows at or after its converted `since`. Even manual refresh bypasses only the polling gate; it does not remove the notice time filter or request every historical page. Local cache accumulation does not recover history never fetched on that device. A comment calling a first/manual fetch “everything there is” refers to this repository's workflow, not #31's complete inbox. Neither the direct-list model nor the fetch path reads a notice pager or category result bounds. [Bounds][fetch-bounds] [Selection/filter][api-list-path] [Model filtering][notice-window]

Do not interpret `counts.notice`, full `note` strings, an all-unread list, an empty list, or agreement on a few rows as proof of all reply, mention, system and social-activity categories, all pages or all history. The executable caller gives no complete-notice pagination contract; this research did not inspect the owning server query/limit. `category` appears in fixtures but is not mapped into the displayed notice model. **Recommendation:** retain current `home.php?mod=space&do=notice` HTML/page-JSON category and returned-pager paths for #31's complete standard notices, with each category/page requested deliberately and its effects disclosed. Follow the returned forum controls; this note does not invent category query values or API cursors. Populated current category/pager behavior remains a named downstream observation. [Fixture fields][fixtures-shape] [Model][notice-model] [#31][notice-ticket]

`time` is the API's server clock, separate from device time and row timestamps. The native converter deliberately matches a legacy page-parser bug: it shifts Unix seconds by the member's `timeoffset`, constructs that wall clock as device-local time and truncates to minutes. The API filter bound is converted in the same representation to avoid dropping new rows when device/forum zones differ. The future fetch bound uses the earliest known server clock/Date header, minus a minute after truncation; device start time is a fallback when no clock is known. These are compatibility policies, not accurate general-purpose UTC timestamp conversion. **Recommendation:** keep server instants, member display offset and read-effect bound distinct in the browser model; preserve precision and avoid copying the legacy bug merely to match native cache equality. Qualification must include different device/forum zones and repeated IDs. [Conversion][time-conversion] [Clock/bound helper][clock] [API-list path][api-list-path]

### `seen`: content loading and acknowledgement are distinct operations

The native repository's `_markSeen` posts once through `TsdmAppApi.post`:

```text
POST plugin.php?id=tsdmapp:api&action=seen
formhash=<current-account token kept in memory>
notice=<notify.time>    # optional server-clock bound, not a notice ID
pm=1                    # optional, independent request to clear the PM prompt
```

`postForm(..., singleAttempt: true)` performs one attempt and follows no redirect, per the API transport contract. A non-JSON response, transport failure, busy/off/action error or invalid formhash is not proof the plugin disappeared. In particular the client documents Discuz's pre-plugin HTTP 503 System Error page for a rejected token. [POST implementation][api-post] [Form construction/outcome][seen]

The client documents the server effect as **mark every unread notice read unless any unread notice has a timestamp at or after the supplied clock**. The `newer` result signals arrival or re-marking after/in the response clock; Discuz can update the same ID in place, so an ID bound would be unsafe. This is account-level notice scope, not per-ID or category/page acknowledgement, and not “mark only the fetched rows.” An inspected fixture scenario supplies an unread row older than the retained window and expects a `seen` request even though that row is dropped from the local result. The code also retries this acknowledgement during a later otherwise-empty poll while `notify` still lists unread notices. [Documented bound semantics][api-lists] [Fetch/idle retry][fetch-selection] [Nonempty window fixture][fixture-flow]

The optional `notice` and `pm` form fields provide **client-side evidence of separable intent**: tests expect notice-only and PM-only forms; the combined refresh can request both. Omit `pm` for a notice-only browser action. However, no owning plugin source was available in the inspected tree, and the stubbed tests cannot prove transaction scope, the global newer-row guard, same-second races, omission of PM effects, or rollback behavior. Retain this server-contract uncertainty until server source or bounded authorized readback confirms it. Do not claim PM prompts remain unchanged merely from omitted form fields. [PM-only fixture][fixture-pm] [Combined form fixture][fixture-refresh] [Form construction][seen]

The native policy waits at most eight seconds, logs failure and returns the content result; timeout does not cancel the request. Its eventual server effect is therefore uncertain even after the UI resumes. A later native poll may send `seen` again. A bound ahead of the API server clock suppresses notice acknowledgement because that window was not fetched. These are native synchronization choices; #31 requires deliberate actions and no background polling. **Recommendation:** represent content outcome and read-effect outcome independently, retain uncertainty after response loss/timeout, and allow only a new deliberate action or an authorized authoritative readback. Do not silently follow a possibly completed `seen` with read-affecting HTML fallback or automatically replay it on Back/Forward/reload/remount. [Native timeout][seen] [Future-clock fixture][fixture-future] [#31][notice-ticket]

## Exact targets and the existing browser ownership boundary

At the required starting revision, notice detail called `fetchDocument`, decoded HTML/page JSON and located `div#post_<pid>` using `pid` and `ptid` in the notice target. The refreshed revision adds `fetchNoticeThread`: same JSON-preferring URL helper, but `threadApiAnswerOf` is selected before the document guard, and a supported schema-3 response builds `ThreadPageInfo`. The detail cubit selects the exact returned post ID, uses the returned actual page/closed/reply parameters, fails when the target post is absent, and withholds a mismatched thread's report target. Old/no-plugin/document responses retain the actual redirect page and HTML parser. This is a relevant refresh of #2's “notification target reads HTML” claim. The current changelog still says notice detail reads page fragments; executable current source and its test_215 are newer than that sentence, so that sentence cannot establish the refreshed target path. It is still source evidence, not proof of Tampermonkey redirects or remounts. [Current target request][target-request] [Current detail selection][target-detail] [Starting detail][starting-detail]

The existing UI forum client already accepts canonical `forum.php?mod=redirect&goto=findpost&pid=…` and last-post routes. Its thread read path prefers JSON but presently requires `document`, accepts useful HTML from that same request and returns document-navigation state when the host must perform a real redirect. The workspace owns origin/selection/position and opaque history entries; the host owns `history`, tab-local navigation storage and full-document navigation. `show`, `restoreHistory` and a recovered entry in `start` restore snapshots rather than fetching them. The browser address is a safe `forum.php#workspace=<opaque-key>` URL. [UI routes][ui-routes] [UI reader][ui-reader] [Workspace restoration][ui-restore] [Navigation host][ui-host]

Notices are currently only a saved section overview with a native link. `openSection('notices')` creates the overview entry without invoking `read`; `refresh` only handles boards/search. Neither `ReadResult`, the route allowlist nor navigation-record validation currently implements a notice inbox. Therefore the source establishes a useful existing ownership seam and no-preload overview, **not a delivered #31 passive notice list**. Adding a serializable notice model/category/pager and its existing record validation belongs to future #31 work. Do not add an independent history/storage owner. The later writing branch is not used as notice implementation evidence here. [UI overview][ui-layout] [Section behavior][ui-sections] [Record validation][ui-record] [#31][notice-ticket]

**Recommendation:** save the deliberate notice result, category/page, selected notice and target, position, account generation and truthful effect state in the existing navigation record. Thread/exact-post opening uses the forum client's destination interpretation and the host's established remount handshake. Return restores that local list without `notify`, `seen` or notice-page requests. A missing/invalid snapshot offers explicit recovery without fetching; direct native notice arrival discloses possible pre-startup read effects before any further deliberate load. Restored server unread information is stale, not freshly zero. Exact-post metadata helps choose a destination but cannot prove host redirect persistence. [#31][notice-ticket] [ADR][adr] [Workspace restoration][ui-restore]

Full notice `note` remains forum-origin HTML. In a browser, pass it through the existing inert content conversion and validated serializable model, retaining supported bodies/links and explicit unsupported-content notices. Never execute returned scripts or attach event handlers copied from HTML. Upstream's detached HTML normalization is not the browser renderer's security boundary. The current UI uses parse5 plus allowed tags/URLs/attributes, and `ContentView` renders those typed nodes; recovery validates them again. PM/broadcast summary text handling in the native card is a distinct compatibility boundary and does not justify rendering arbitrary summaries as HTML. [Notice conversion][notice-conversion] [UI inert conversion][ui-content] [UI renderer][ui-renderer] [UI stored-node validation][ui-record] [Native summary/card][notice-card]

## Compatibility context without scope expansion

`pmlist` exists because `notify.pms` lists unread received conversations and cannot establish a complete conversation list. The native app calls it after a PM-change signal or on refresh, can fall back to the private-message page, and clears the PM prompt only when appropriate to that path. Its separate response expects UID/time offset and PM rows; this does not make PM delivery part of #31. `notify.announces` contains unread broadcasts; the native first/manual refresh still reads the broadcast page to include read messages. Neither is a standard-notice category or proof of an accepted complete broadcast inbox. PMs, a broadcast inbox, automatic polling and local native read/unread controls remain deferred. [PM path][pm-path] [API-list path][api-list-path] [#31][notice-ticket]

## Research gaps and operation-specific recommendation

Proceed with #31's existing HTML/page-JSON **complete category/page** design and shared restoration owner. The API is a candidate for a separately validated deliberate read of the rows it actually supplies; it cannot replace complete standard-notice navigation on the evidence here. Validate returned shape/account, preserve partiality and effect state, and never start background polling merely because `notify` is cheap. Add a separate explicit `seen` path only after its account-wide scope and PM independence meet the accepted workflow and owning contract/readback is known. Keep HTML fallback under the same deliberate action and avoid another read-affecting request after uncertain effect completion.

The downstream gates are (1) current deployed capability and populated categories/pagers, (2) owning server semantics for time-bound `seen`, concurrent arrivals/re-marking, scope and PM coupling, (3) exact candidate installed redirects/remount/passive history in Edge and Chrome, and (4) full-body inert rendering with nonempty notices and accurate stale/unknown state. None blocks delivery of this source-only research; each can block the dependent production claim. No throughput/byte-saving benchmark, plugin deployment, complete inbox, server transaction isolation or installed behavior is inferred from the inspected source.

## Actual trade-offs
