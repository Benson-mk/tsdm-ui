# Structured board-browsing API evidence

Issue: [#44 — Refresh structured board-browsing API evidence](https://github.com/Benson-mk/tsdm-ui/issues/44). Inspected on 2026-10-20 (Asia/Hong_Kong).

A valid plugin 2.0.0 board answer can supply the board, populated thread rows, supported filters, subboards and pagination without the old whole-page `document`. The current TSDM UI still consumes the HTML inside that envelope. A future integration can remove those board selectors, but must preserve returned board/viewer identity, separate moved-row identity from its target, retain the existing result-return workflow and reject incomplete structured answers instead of displaying false emptiness. `forum.rules` remains HTML. This note changes evidence only; it implements no decoder, UI, authoring or release behavior.

## Request to visible workflow

**Source-inspected, upstream path:** `ForumRepository.fetchForum(fid, filterState, pageNumber)` builds the ordinary same-host `forum.php?mod=forumdisplay&fid=…&page=…&forumdefstyle=yes` URL, applies only the selected query/filter values and adds `tsdmapp=json`. `forumdefstyle=yes` requests the normal row representation for picture-mode boards and may affect the forum's view cookie. The request is a page URL, not `plugin.php?action=forum`. Using the configured `www` host preserves host-only account cookies; this native host choice does not prove Tampermonkey session isolation. [Repository][forum-repository]

The successful HTTP response is passed to `forumApiAnswerOf`. For `ok:1`, a numeric `schema >= 2` selects direct structured conversion. For `ok:0,error:"message"`, either that schema marker or integer `login` selects a structured refusal. Other answers use the existing same-response page-document path; an answer without a usable page fails first. There is **no automatic second board fetch** merely to obtain another representation in this repository method. [Selection][api-selection] [Repository][forum-repository]

`forumPageFromApi` creates the existing `ForumPageData`: it divides ordered rows by `displayorder > 0`, uses `NormalThread.fromApi`/`StickThread.fromApi`, maps subforums through `Forum.fromApi`, and returns filter menus and returned page numbers. `ForumBloc._mergePage` merges this data into visible state. `ForumPage` renders its normal/pinned/subboard tabs and filter controls; `NormalThreadCard` opens the constructed `threadID`. A moved row therefore opens its **target** identity from the model, rather than its original pointer `tid`. The view can offer poll creation for the matching current account, but that is native-client context and does not add polling or poll creation to the first-release UI scope. [Conversion][api-converter] [Rows][normal-thread] [State merge][forum-bloc] [Native view][forum-view] [Card target][thread-card]

**Source-inspected, current UI path:** the real layout invokes workspace navigation, which calls the shared forum client and browser transport. `readPage` adds `tsdmapp=json`, makes one request and passes board/directory responses to `decodeBoard`. The decoder checks the returned URL origin, route kind and requested board `fid`, and accepts HTML/JSON media types. JSON must contain string `document`; it joins optional `head` with that HTML and uses inert `parse5` parsing. It never reads schema 2 fields. A valid structured-only fixture is consequently **invalid in this UI today**, while a schema 2 envelope with complete compatible `document` can still work through the old path. Useful ordinary HTML returned with its HTML media type to the JSON-preferring URL is consumed directly. HTML mislabeled `application/json` is currently rejected. [Client request][ui-client] [UI decoder][ui-board] [Inert HTML][ui-html]

`decodeBoard` yields serializable `Board`/`ThreadRow` data: actual board ID/title, subboards, row identity and destination, pinned/moved markers, category, author/date/count text, last-post links, available filter links, criteria and returned pages. The Vue layout displays those links and rows; workspace snapshots retain the origin/selection/useful position for return. This boundary is already delivered by #17. A future structured decoder belongs inside the forum client; it must return the same workspace meanings, without moving response interpretation into the layout. [Current types][ui-types] [Visible rows][ui-layout] [Workspace observations][ui-workspace] [#17](https://github.com/Benson-mk/tsdm-ui/issues/17)

## Identity and account changes need explicit preservation

**Source-inspected:** native `forumPageFromApi` can label a response using requested fid despite a different `forum.fid`, and `forumApiAnswerOf` accepts any numeric schema at least 2 for success without checking the response's `type`. Thus the client is evidence of a useful data contract, not a validator suitable to copy without qualification. Required-field helpers default missing objects/lists/text/integers to empty/zero; a malformed `{"ok":1,"schema":2}` can become an apparently successful empty board. This is a source-derived reachability finding, not an executed failure. [Selection and helpers][api-converter]

The current UI guards the response URL identity and discards a superseded in-flight request. It updates the account generation when decoded actor identity changes. Workspace handling invalidates incompatible visible results, origins and stored snapshots when a known member/guest change is observed. These guarantees must remain when a structured path supplies `uid`. Top-level uid provides a response-scoped viewer claim; a positive uid must remain distinct from guest 0 and unknown/missing/wrong-typed uid. A schema message's `login:0` establishes permission refusal, not which member is viewing it. The present `Account` model also has a display name, whereas these board fixtures do not supply a top-level viewer name: do not borrow a thread author's name to fill it. [UI request/generation][ui-client] [Workspace invalidation][ui-workspace] [Account shape][ui-types]

**Future requirements:** reject contradictory returned fid/type, preserve original row and actual target identities, update generation on fresh authoritative viewer changes, prevent late old-generation results replacing the new account, and keep unknown identity visible. A member-to-guest/other-member failure must remove old-account content; a same-account or unknown network failure may retain clearly stale content according to the existing workspace policy. These are migration expectations at the current application boundary, not new account isolation promises.

The agreed seam is the complete **layout → workspace → forum client → host** application, replacing only external network responses for deterministic cases; its machine-readable receipt, human report, request ledger and deliberately authored visible artifact should record source/build identity. ## Trade-offs

This is the canonical ledger of shared investigation choices for #44, #45 and #46. Each actual shared trade-off is recorded once here; the other notes link here and record only their distinct operation-specific recommendations.

1. Use three independent workflow notes, isolated worktrees and shared source pointers for concurrent investigation. This keeps the work bounded and independently reviewable, at the cost of repeated version context and coordination, including shared-file handoffs when delegated messages lose their text.
2. Inspect primary client source, populated fixtures and existing assertions without a new executable probe or live forum operation. This answers the evidence tickets without account/read-state effects or a replacement client, but does not establish owning-server implementation, deployment, parser execution, installed behavior or performance. Named downstream cases retain those gaps.
3. Separate evidence from production migration and preserve completed delivery tickets. This avoids duplicating delivered work or expanding scope, while structured adoption remains subsequent implementation.
4. Link standalone follow-ups to historical research and delivery rather than rewriting parents or closed tickets. This preserves provenance, at the cost of readers following multiple evidence links.
5. Inspect both the required starting revision and the refreshed upstream revision, with executable code taking precedence over stale prose. This captures newer readers and contract changes, at the cost of maintaining two explicit baselines and explaining release/Unreleased differences.
6. Publish authored summaries, immutable source citations and portable replay instructions instead of raw fixture/member/token content or local snapshots. This protects forum/account data, while readers need the pinned repositories and their own authorized observations for full reproduction.
7. Compare against the delivered UI integration rather than documentation-only main. This reflects actual browsing/download/navigation behavior, at the cost of replaying a separately pinned integration source. That source is already public; no application-code publication is needed for this research.

The thread note records the distinct cost of retaining structured and HTML interpretation per operation. The notice note records the distinct complete-inbox and effect-state recommendations. These are future integration trade-offs, not production behavior implemented by these research tickets.
