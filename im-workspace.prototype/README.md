# IM workspace interaction study

**2026-10-18 update:** the confirmed [Text size follow-up](TEXT-SIZE.md) replaces the density selector with global 70%–150% text scaling and automatic workspace-wide Compact spacing below 100%. That record contains the current acceptance checks, replay instructions and complete new trade-off ledger. The original comparison and its 2026-10-16 evidence remain available below.

Disposable prototype for [Define the modern IM forum workspace](https://github.com/Benson-mk/tsdm-ui/issues/6). The human selected **A — Workspace** as the desktop base on 2026-10-16 and requested that the secondary pane follow main navigation. The human then chose section overviews in place of the previous reader/composer when changing main sections, and accepted the medium-width picker plus narrow-screen drill-down structure. Both choices are implemented. Precise workflow semantics remain with the separate behavior decision.

Run `python3 serve.py`, then open `http://127.0.0.1:4176/im-workspace.prototype.html?variant=A`. Use the bottom arrows (or left/right outside an editor) to compare A, B and C. The variants use identical synthetic forum content. The page also opens directly as a local HTML file with its adjacent CSS and JavaScript.

| Variant | Interaction proposal | Cost to judge |
| --- | --- | --- |
| A — Workspace (selected base) | Persistent section navigation, results and an overview/reader pane; reply below the reader | Reading width; the section pane becomes a picker below 1280px |
| B — Reading | Top navigation and centered reader; browsing picker; reply below the posts | An extra step to browse, and travel to the inline composer |
| C — Desk | Combined navigation, session-only open-thread tabs; side composer at 1280px and above | Extra open-view state and narrower reading while composing |

The accepted responsive structure collapses A’s secondary pane into a picker at medium widths, then uses one pane at a time on narrow screens. Below 960px in this prototype, each variant uses explicit section context → results → thread navigation. The back button walks outward. C retains scrollable open-thread tabs. The breakpoints are prototype values to exercise the proposed structure. The first release's responsive presentation requirement does not establish mobile-browser installation support.

The secondary pane now follows the main destination: Boards shows its directory, Search shows synthetic board scopes, Saved shows thread/board views, Notices shows the current-account inbox and Drafts shows unpublished threads. The same choices appear in the picker. Choosing a Search scope keeps Search active; opening a saved board enters Boards. These fixture categories demonstrate placement and do not settle real search capabilities or notification categories. Changing a main section replaces the reader with that section’s overview and hides the previous posts and composer. Selecting a result opens its content. The editor remains mounted in memory, with a labeled Return to writing action; a compact header shortcut keeps that action reachable when the overview pane is offscreen. New-thread writing has its own contextual heading without unrelated old posts. These retention helpers make the geometry demonstrable without settling production unsaved-transition or draft persistence semantics.

Use Appearance to try Light, Alias, Mono and Dark; Text size from 70% to 150%; Traditional Chinese, Simplified Chinese and English. Interface language does not translate forum fixture content. Text size affects the whole workspace. Compact spacing is automatic at 70%–90%; Default spacing applies at 100%–150%, with control target minima preserved.

The study controls expose permission, challenge and missing-content scenarios plus an unknown submission outcome. All results, attachment controls and drafts are illustrative. No forum requests, uploads, downloads or account operations occur. Only text size persists in a dedicated prototype browser key; reload discards other demo state, including writing. The text field and disabled toolbar illustrate composition placement; they are not a rich-text or BBCode editor implementation. Detailed workflow behavior remains with [Specify the first release's detailed workflow behavior](https://github.com/Benson-mk/tsdm-ui/issues/10).

## Original decisions and trade-offs — 2026-10-16

1. Plain HTML/CSS/JavaScript avoids selecting a production framework, but the code is disposable and supplies no application architecture.
2. Synthetic fixtures and simulated outcomes make the comparison safe and repeatable, but establish no backend or installed-runtime evidence.
3. Three structurally different layouts expose navigation costs, but take more comparison effort than a single recommendation. Shared content and the same destination set keep the comparison fair.
4. A keeps section/list context visible, at the cost of reading width and an extra context-picker step in intermediate windows.
5. B gives space to long posts, at the cost of opening the picker to browse and reaching the composer below the posts.
6. C keeps parallel thread context and side-by-side writing, at the cost of session tabs and a narrower reader while composing. Tabs are open views, not persistent reading history.
7. Narrow drill-down preserves readable posts and touch targets, at the cost of simultaneous context. The same narrow base behavior reduces divergence between variants.
8. Approved palettes, typography and post densities preserve the supplied visual language. Pane layouts deliberately depart from DESIGN.md's page cap, outer gutters and top-navigation geometry. The working reader omits editorial hero/footer compositions; B retains a centered text measure. The human selected A’s workspace geometry; exact styling and breakpoint numbers remain illustrative.
9. In-memory state keeps the artifact disposable and avoids introducing an application draft store, but reload loses input, preferences and open tabs. This does not amend the eventual forum-only draft or saved-preference contract.
10. Bounded E2E walkthroughs, screenshots and source hashes provide repeatable interaction evidence, but are not production test suites or full accessibility/locale qualification. Targeted intermediate widths add effort to expose pane-width failures without running the entire production matrix.
11. The text field, disabled editor toolbar and synthetic drafts/attachments show placement, at the cost of leaving rich/source conversion and complete authoring behavior untested. The existing workflow decision still owns those details.
12. Showing the same destinations and account entry in all layouts adds placement-only views, but prevents a variant appearing simpler by silently omitting accepted scope. Synthetic search and favorites demonstrate navigation only; board-favorite operations and server semantics are not qualified.
13. The composer remains attached to its original target while browsing, making reference switching possible, but readers must distinguish the visible thread from the explicitly labeled writing target. A prompt prevents replacing typed content when starting another target. This behavior is a proposal to discuss, not a resolved product requirement.
14. System font fallbacks and simple glyph icons avoid asset/network dependencies, but actual font weights and icon appearance vary by platform. The inline SVG is synthetic post media, not a new interface palette, and retains its colors in every theme.
15. Per-pane scrolling and a capped composer keep navigation and writing reachable, at the cost of multiple scroll regions. B uses one reading flow on desktop; the others expose that comparison deliberately.
16. Preferences preserve mounted editor/post nodes and visible reading context during restyling. Navigation uses recreated fixture posts and session scroll offsets instead of a production view cache, keeping the prototype small but not proving full navigation-state preservation or undo/IME behavior.
17. A local worktree and temporary build keep the primary checkout's existing untracked design files untouched, but require a later capture commit once the human decision is complete. The artifact belongs on its throwaway branch; it is not application implementation.
18. Deriving the secondary pane from the active destination removes misleading board navigation, but adds small destination-specific choices. Search scope and favorite-view selection live in the existing in-memory state rather than a new routing/store abstraction.
19. The inbox and unpublished-thread views use one conservative entry each, and Saved boards has one synthetic fixture. This demonstrates placement without inventing read-state categories or server operations, but gives less varied content than a complete workflow.
20. Reusing the same choices in the sidebar and picker keeps context consistent across widths and B/C, but gives the compact picker more controls. The outward narrow level is now the current section's context rather than always a board directory.
21. The human selected section overviews in place of the earlier retained-reader proposal. This makes a section switch unambiguous and removes unrelated posts/composition from view, at the cost of losing simultaneous reading/reference context and requiring a result selection or Return to writing action.
22. Search text, scope and favorite view are stored in existing browser history, and typing replaces the current entry. Back restores useful context without a keystroke-per-entry history, at the cost of additional view-state bookkeeping; the open picker must refresh too, and entering new-thread writing adds a view transition. This is session history only, not persistent drafts or a production URL contract.

23. An explicit overview/thread/writing view distinguishes section entry, reading and new-thread authoring. It prevents unrelated old posts from appearing behind a new thread, at the cost of one additional view discriminator and visibility coordination with recovery, tabs and the composer.
24. Keeping unfinished input mounted and providing Return to writing avoids silently discarding work when hiding the composer. The overview action and compact header shortcut use interface space and add a return step; they do not introduce saved local drafts or settle the production transition contract.
25. Applying the overview visibility rule to the shared reader surface keeps A/B/C behavior comparable and avoids stale C tabs/side columns. It changes the archived comparison variants too, so the earlier screenshots and source hashes are retained as a separate historical stage rather than presented as the final artifact.
