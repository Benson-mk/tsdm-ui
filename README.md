# TSDM Workspace

Public application versioning starts at **0.1.0**. You choose release versions by
pushing tags; builds and release-page notes wait for your explicit approval
before publication. See [release automation](docs/releases/AUTOMATION.md) for
preview, approval, downloadable builds and qualification requirements.

## Quick Start

1. Install [Tampermonkey](https://www.tampermonkey.net/) in your browser.
2. Open [Releases](https://github.com/Benson-mk/tsdm-ui/releases), choose a version,
   and download **`tsdm-workspace.user.js`** from its Assets. Import the file into
   Tampermonkey and confirm the displayed version matches your chosen release.
   Keep exactly one enabled TSDM Workspace script.
3. Open or reload [TSDM](https://www.tsdm39.com/). The workspace uses your current
   forum account and includes its runtime; no separate library download is needed.

Updates are manual: download the new version and replace the existing script.
Before updating or downgrading, finish writing, save a supported forum draft, or
copy your text somewhere you control. Browser page-session recovery is conditional;
refreshing, closing or restarting can lose local writing. Check an unresolved
publication attempt before sending again.

To return to the native forum, disable the userscript or add `tsdm-native=1` to
the forum URL query while preserving its existing parameters and destination.

Build and synthetic checks do not establish installed browser qualification.
Windows support and actual Tampermonkey software-update recovery remain unverified.
See [release automation](docs/releases/AUTOMATION.md) for build verification and
the [qualification scope](docs/adr/0002-qualify-installed-releases-with-bounded-evidence.md).

## Replace or roll back a candidate

Follow the [replacement rehearsal](docs/implementation/35-replacement.md#installed-rehearsal) with the retained earlier bytes and the newly frozen candidate. Before replacing, finish writing, confirm a supported forum save, or copy complete source and necessary options somewhere you control. Replies and edits have no invented draft-save operation. Preserve unknown attempt identity and its submitted revision before replacement; never resend merely because the script changed. Resolve pending operations or retain them as uncertain. Browser page-session recovery is helpful but is not a durable backup.

Replace the existing **TSDM Workspace** script with namespace `https://github.com/Benson-mk/tsdm-ui`; do not install a second identity. The script has no automatic-update metadata. Export and hash the manager-stored source before and after replacement, confirm exactly one enabled copy, and reload. Compatible theme, language and Text size restore with spacing derived from Text size. An incompatible writing record stays available through **Inspect retained recovery data**; copy its source before explicit local reset. Incompatible preferences are retained in Settings for copying until explicit reset. Changes preview on the current page without overwriting that retained preference record.

For downgrade, copy source, title, options, target/account and unknown-attempt details **before** installing older code. Older code may not understand newer records or protect them. Keep the newer exact artifact for returning. If the older code cannot recover, use your copied text deliberately with a freshly prepared current-account form; do not replay old attempts. Reset local state only after preserving what you need. Local discard, script disable and uninstall never delete forum posts, drafts or uploads; remote cleanup is a separate action.

If startup fails, use the manager's native-recovery command when available. If even the script cannot run, disable it and open the original native destination with `tsdm-native=1` added to its query, keeping its `#pid…` anchor. An opaque `#workspace=…` URL needs a compatible stored record to resolve the exact destination; without one, return to native Boards and locate the target. To re-enter, enable one script, remove only the bypass parameter and reload. Manager disable/uninstall may leave browser-origin preferences and page-session records; neither is server cleanup or guaranteed durable retention.

## Recovery contract

The [accepted page-session decision](docs/adr/0003-use-browser-page-session-recovery.md) uses one versioned `sessionStorage` record, `tsdm.workspace.recovery`, for navigation, token-free Search context and writing. Schema 2 retains source, title, current options, action, board, original account, uploaded reference identities and selected source range. Cookies, form tokens and unuploaded file bytes are excluded. Every change is serialized through one queue and acknowledged by exact readback. Refused storage keeps live writing visible and identifies unacknowledged changes; there is no second recovery store or silent eviction. History holds safe URLs and opaque keys only. Valid schema 1 navigation records migrate with no writing context. Incompatible or malformed raw records remain available for inert inspection until deliberate reset.

Recovery follows the browser page session: an opener-created or browser-restored tab may inherit a copy, then diverges independently. Closing/restoring and application replacement recover only when the browser supplies a compatible record. Same-origin scripts can read or modify it. A restored context retains its original account and pauses sending until a fresh check. Explicit text copying prepares the current account's form and requires confirmation before replacing the sole context; it transfers title/source only, clears uploaded identities, and flags unresolved attachment references. Local retention itself performs no submission; Save forum draft is a separate explicit server operation for supported thread compositions. Publication attempts are immutable account-bound snapshots alongside current writing. Pending attempts restore as uncertain without replay or automatic checking. A result check retains the original attempt; an inconclusive check requires an explicit duplicate-risk warning and fresh preparation before another attempt. Deliberate text copying retains old attempt history, and pending publication/result checking blocks context replacement.

The historical [#19 acceptance audit](docs/implementation/19-acceptance.md) separates the complete synthetic baseline and affected installed correction checks for that ticket’s f36 candidate from historical c855 native-input and lifecycle observations. For that historical f36 candidate, full installed qualification remained incomplete: no manager update was offered, and native CJK input, the complete appearance matrix and the full lifecycle baseline have not been repeated on f36.

Old development candidates used a GM-only navigation record. That record is not migrated or read alongside the new store. An old opaque URL without a browser session record shows unavailable recovery and offers explicit Reload or safe native Boards continuation.

Ordinary-thread publication exposes `prepareThreadPublication(submission)`, `publishThread(attempt)` and `checkThreadResult(attempt, candidateURL?)` with serializable `ThreadSubmission`, `ThreadPublication` and `ThreadAttempt` models. Preparation binds the exact revision/account/board/current options, supersedes older same-context forms and keeps native secrets private. Each send requires fresh preflight; duplicate or changed preparations refuse without POST. A native callback supplies a candidate only: fresh opening-post identity/author and complete editable source/persistent-options readback decide stored-publication confirmation. Failed preflight is known not sent, while a lost POST response or changed in-flight account stays uncertain. The host/caller must acknowledge the original pending attempt before calling `publishThread`; the browser workspace enforces this through its sole recovery owner. Ambient account changes have no atomic isolation or rollback guarantee. See [the #20 failure inventory, verification and trade-offs](docs/implementation/20-ordinary-threads.md).

Only the named checkbox creation instructions `addfeed`, `adddynamic` and `adddynamic_doing` are distinguished from stored options. Each retains requested state and actual command inclusion. Requested delivery stays `unknown`; an unchecked instruction is `not-requested`, not proof that no external effect occurred. A callback feed identifier and an absent owned-edit checkbox establish no delivery guarantee. The bounded matching guarded literal `succeedhandle_` variant remains candidate-only; arbitrary names or script execution are unsupported.

Schema 2 retains legacy uncertain attempts unchanged, so an original saved attempt can gain the new evidence through explicit GET-only `checkThreadResult`. Compatible legacy confirmed results may lack `verification` and are labelled as previous evidence by the workspace. New evidence is strictly validated against the immutable submission; malformed evidence remains incompatible and inspectable. Recovery validates structure and consistency, not authenticity against forum-origin scripts. A failed recheck retains known stored confirmation with an explicit failed-current-check explanation rather than discarding prior evidence or offering an uncertain-publication resend solely for unknown effects. It does not establish current freshness. Later writing remains separate and no result check repeats a send.
