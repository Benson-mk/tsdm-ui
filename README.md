## Recovery contract

The [accepted page-session decision](docs/adr/0003-use-browser-page-session-recovery.md) uses one versioned `sessionStorage` record, `tsdm.workspace.recovery`, for navigation, token-free Search context and writing. Schema 2 retains source, title, current options, action, board, original account, uploaded reference identities and selected source range. Cookies, form tokens and unuploaded file bytes are excluded. Every change is serialized through one queue and acknowledged by exact readback. Refused storage keeps live writing visible and identifies unacknowledged changes; there is no second recovery store or silent eviction. History holds safe URLs and opaque keys only. Valid schema 1 navigation records migrate with no writing context. Incompatible or malformed raw records remain available for inert inspection until deliberate reset.

Recovery follows the browser page session: an opener-created or browser-restored tab may inherit a copy, then diverges independently. Closing/restoring and application replacement recover only when the browser supplies a compatible record. Same-origin scripts can read or modify it. A restored context retains its original account and pauses sending until a fresh check. Explicit text copying prepares the current account's form and requires confirmation before replacing the sole context; it transfers title/source only, clears uploaded identities, and flags unresolved attachment references. Retention itself performs no submission and offers no Save forum draft action. Publication attempts are immutable account-bound snapshots alongside current writing. Pending attempts restore as uncertain without replay or automatic checking. A result check retains the original attempt; an inconclusive check requires an explicit duplicate-risk warning and fresh preparation before another attempt. Deliberate text copying retains old attempt history, and pending publication/result checking blocks context replacement.

The [#19 acceptance audit](docs/implementation/19-acceptance.md) separates the final f36 candidate’s complete synthetic baseline and affected installed correction checks from historical c855 native-input and lifecycle observations. Full final-candidate installed qualification remains incomplete: no manager update was offered, and native CJK input, the complete appearance matrix and the full lifecycle baseline have not been repeated on f36.

Old development candidates used a GM-only navigation record. That record is not migrated or read alongside the new store. An old opaque URL without a browser session record shows unavailable recovery and offers explicit Reload or safe native Boards continuation.
